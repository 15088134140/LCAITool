# Agent 工作流规范

## 子代理工作流规范

本项目所有子代理任务必须遵循以下规则。

### 禁止子代理自行执行 git commit

子代理（implementer）只负责写代码，不执行 `git commit`。

- 子代理完成工作后，只需要在报告中列出所有修改/创建的文件路径清单。
- git commit 操作统一由父代理（父会话）按任务批量执行。
- 原因：子代理隔离环境中的 git 操作可能静默失败，导致“报告说已提交，实际没提交”的不一致问题。

### 派遣子代理的标准 prompt 必须附加规则

父代理每次构造子代理 prompt 时，末尾必须加上这一行：

```text
⚠️ 重要规则：不要执行 git commit 命令！完成后只需要列出你修改/创建的所有文件路径，提交操作由父代理统一执行。
```

### 父代理提交责任

子代理完成实现后，父代理应：

1. 查看子代理列出的文件清单。
2. 运行必要验证。
3. `git add` 相关文件。
4. 按任务单独 `git commit`。
5. 向用户报告“已完成并提交”。

提交信息格式：

```text
feat: 实现 XXX (Task N)
```

## Agent 派遣规则

Agent 不会自动触发，父代理应根据任务类型显式派遣。派遣子代理时必须继续遵守上方“不执行 git commit”的规则。

### 默认派遣优先级

| 任务类型 | 优先派遣 Agent | 典型场景 |
| --- | --- | --- |
| 产品范围、用户价值、路线图 | 产品经理 | PRD 梳理、范围裁剪、用户路径、商业目标对齐 |
| 规格拆解、任务排期、实施切片 | 高级项目经理 | 将 PRD / 设计文档拆成可执行任务，控制 MVP 范围 |
| LLM 应用、Provider、Prompt、RAG、Dify、回调、Token 成本 | LLM 应用工程师 | AI Provider 抽象、Prompt 版本化、执行器、任务队列、流式响应、工具调用、成本治理 |
| 后端 API、Service、权限、业务状态机 | 后端架构师 | FastAPI 接口、服务层设计、任务状态流转、鉴权与数据边界 |
| 数据库 Schema、Alembic、索引、慢查询 | 数据库优化师 | migration、查询优化、索引策略、数据一致性 |
| 前端功能、组件实现、页面交互 | 前端开发者 | React 组件、状态管理、API 对接、交互实现 |
| UI 视觉、组件规范、设计一致性 | UI 设计师 | 页面视觉、组件样式、设计系统一致性 |
| UX 流程、信息架构、可用性 | UX 架构师 | 多步骤流程、表单体验、导航与交互结构 |
| 安全、权限、隐私、资金、支付、敏感数据 | 安全工程师 | 威胁建模、越权检查、敏感数据保护、支付/资金风险审查 |
| CI/CD、部署、环境变量、运行时配置 | DevOps 自动化师 | 部署流水线、环境配置、监控告警、回滚策略 |
| Git 分支、rebase、worktree、提交组织 | Git 工作流大师 | 分支策略、冲突处理、提交拆分、PR 准备 |
| API 验证、接口契约、集成测试 | API 测试员 | 接口测试、鉴权测试、错误码与边界验证 |
| 测试证据、验收材料、质量报告 | 证据收集者 | 收集测试输出、截图、日志、复现步骤 |
| 上线前放行、生产就绪判断 | 现实检验者 | 验证证据是否充分，判断是否仍需改进 |
| 代码正确性、可维护性、安全性审查 | 代码审查员 | diff review、潜在 bug、安全与性能风险 |
| 文档、README、API 说明 | 技术文档工程师 | 开发者文档、接口文档、使用说明 |
| SEO、公开站点自然流量 | SEO专家 | Landing page SEO、结构化数据、搜索增长 |

### 多 Agent 协作建议

- **AI 功能开发**：LLM 应用工程师 → 后端架构师 → API 测试员 → 代码审查员。
- **涉及计费/资金的 AI 功能**：LLM 应用工程师 → 后端架构师 → 安全工程师 → 证据收集者 → 现实检验者。
- **前端交互功能**：UX 架构师 / UI 设计师 → 前端开发者 → 代码审查员。
- **数据库变更**：数据库优化师 → 后端架构师 → API 测试员。
- **发布与运维**：DevOps 自动化师 → 证据收集者 → 现实检验者。

### 派遣约束

- 子代理用于明确边界的独立任务；需求不清时先由父代理澄清，不直接派遣。
- 多个子代理可并行处理互不依赖的阅读、审查、方案比较任务。
- 修改同一批文件的实现任务不应并行派遣，避免冲突。
- 子代理输出必须包含修改/创建文件清单；父代理负责验证、提交与最终汇报。

## Superpowers + gstack 搭配配置

### Superpowers（思考与流程层）

负责所有 plan、brainstorm、debug、TDD、verify、code review。

触发方式：自动触发。

### gstack（执行与外部世界层）

负责浏览器操作、QA、ship、deploy、canary、安全审计。

触发方式：斜杠命令手动触发。

### 浏览器规则

- 使用 `/browse` 作为唯一浏览器入口。
- 禁止使用 `mcp__claude-in-chrome__*` 操作浏览器。

### 分工裁决

- 计划撰写 → Superpowers: writing-plans。
- 计划多视角审查 → gstack: `/autoplan`。
- 编码 → Superpowers: test-driven-development。
- 调试 → Superpowers: systematic-debugging。
- 真实环境验证 → gstack: `/qa`。
- 代码审查 → Superpowers: requesting-code-review。
- 发布 → gstack: `/ship`。
- 安全审计 → gstack: `/cso`。

可用技能以当前会话的 Available skills 为准，不在本文档中维护完整技能列表。
